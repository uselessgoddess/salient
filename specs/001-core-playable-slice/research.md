# Phase 0 Research: Core Playable Slice

**Feature**: [spec.md](./spec.md) | **Date**: 2026-09-16

Most technology choices are already fixed by [the constitution](../../.specify/memory/constitution.md)
and are not re-litigated here. This document resolves the open questions that the constitution
leaves to the implementation, and records the reasoning so it can be challenged later rather than
rediscovered.

---

## R1. Simulation data structures

**Decision**: Dense struct-of-arrays arenas with generational indices, one arena per entity kind.
No ECS inside `salient-sim`.

**Rationale**: Iteration order must be explicit and stable (Principle III). Arena order is the
insertion/slot order, which is a property of the data, not of an archetype layout that shifts when
components are added. It is also faster for this workload, because every hot phase touches a known
fixed set of fields.

**Alternatives considered**: Bevy ECS inside the simulation — rejected, `Query::iter` order is
explicitly not guaranteed, and pinning it would mean sorting every query every tick. A third-party
ECS — rejected for the same reason plus an added dependency on someone else's ordering guarantees.

---

## R2. Fixed-point format

**Decision**: `Fx` is a newtype over `FixedI64<U32>` (Q32.32). Multiplication, division, and square
root go through `i128` intermediates. Squared magnitudes use a separate wide type, `Fx2`, which is
never truncated to `i64`.

**Rationale**: At a 40 km map scale a raw Q48.16 position is about 2^31.3, so the product of two of
them is 2^62.6 against an `i64` ceiling of 2^63 — Q48.16 needs `i128` anyway, which removes its
only advantage. Q32.32 then buys 16 extra fractional bits for free, which matters across the 24,000
integration steps of a long match. Range headroom is roughly 50,000x what the map needs.

The `Fx2` carve-out is not optional: a squared distance at map scale in Q32.32 is about 1.4e19
against an `i64` ceiling of 9.2e18. Silent truncation here would be a wrong-answer bug in the
hottest code path in the game.

**Alternatives considered**: Q48.16 — rejected above. `f32` with a transcendental ban — rejected;
Rust's basic float ops are deterministic but the ban rests on discipline, and one `libm` call
reaching the simulation through a transitive dependency produces a desync discovered months later.
Q16.16 in `i32` for `i64` products — rejected; ±32768 is too tight for a 40 km map in metres.

## R3. Fixed-point transcendentals

**Decision**: Implement `sqrt`, `atan2`, `sin`, `cos`, and `normalize` in-project. `sqrt` by integer
Newton iteration on `i128`; angles by truncated series evaluated directly, with pinned Q32.32
coefficients.

**Amended during M0 (2026-09-16): no lookup table.** A table would be generated by the same series
that now runs at call time, so it inherits that series' correctness and buys only speed — and speed
is not scarce here. At ten hertz, twenty thousand sine calls cost well under a millisecond against
a hundred-millisecond budget. Dropping the table removes a build-time step and a second thing that
could be wrong.

Angles are measured in **turns** rather than radians, which was not stated before and is worth
recording: it puts range reduction in a bit mask instead of a division by pi, which keeps pi out of
the hot path where its rounding error would accumulate.

**Rationale**: The simulation needs exactly five of these. A table with interpolation is a few
hundred lines, is exact by construction because it is integer arithmetic, and is unit-testable
against a high-precision reference once and forever. Accuracy is irrelevant beyond a bound;
identity is everything, and a table gives identity trivially.

**Alternatives considered**: CORDIC — correct and dependency-free, but slower per call than a table
and harder to reason about. A third-party fixed-point trig crate — rejected; an upstream version
bump that changes one bit is a desync, and this is too small a surface to accept that risk on.

## R4. Determinism enforcement

**Decision**: `clippy.toml` at the workspace root declaring `disallowed-types` and
`disallowed-methods`, applied at `deny` level in `salient-sim`: `f32`, `f64`,
`std::collections::HashMap`, `std::collections::HashSet`, `std::time::Instant`,
`std::time::SystemTime`, and the `rand` convenience entry points. Plus `#![forbid(unsafe_code)]`
and `overflow-checks = true` in every profile.

**Rationale**: Principle III says determinism is a property of construction, not of discipline. A
rule a human has to remember is discipline. A rule the compiler enforces is construction.

Note on hash maps: `std`'s are banned because `RandomState` is seeded per process. A
fixed-seed map such as `FxHashMap` is deterministic for an identical operation sequence and is
permitted, but iteration order must never influence state — dense arenas are preferred regardless.

**Alternatives considered**: Code review — rejected; it is exactly the failure mode Principle III
exists to prevent.

## R5. State fingerprint and recordings

**Decision**: Simulation state serializes through `rkyv` with the `little_endian` feature; the
fingerprint is a `rustc-hash` digest over those bytes. A recording is a header (seed, match rules,
`SIM_VERSION`) plus an ordered list of `(tick, Order)`. A save is either a recording replayed
forward or an `rkyv` state snapshot, at the caller's choice.

**Rationale**: Forced little-endian layout makes the serialized bytes identical across platforms,
so a byte hash is a cross-platform fingerprint with no extra work. One mechanism then covers four
needs — desync detection, replays, saves, and state diffing — which is the difference between
building these and getting them.

**Alternatives considered**: A hand-written per-field hash — rejected; it would drift out of sync
with the state definition and would not also give us saves. Hashing the in-memory representation
directly — rejected; padding bytes and layout are not guaranteed identical across compilers.

## R6. Long-range pathing

**Decision**: Flow fields on a 32 m grid (about 1250 x 1250 cells for a 40 km map), one field per
destination shared by every unit heading there, capped at 32 concurrent fields with
least-recently-used eviction. Field construction is amortised across ticks by a **fixed cell
quantum per tick**, never by a time budget.

**Rationale**: Cost stops scaling with unit count — ten thousand units reading one field cost one
lookup each. A field is about 3 MB at `u16` per cell, so 32 of them is affordable. Destinations
change rarely, so amortisation is invisible.

The quantum detail is load-bearing: budgeting field construction by elapsed time would make the
simulation depend on machine speed, which breaks determinism. The budget must be a count.

**Alternatives considered**: Per-unit A* — rejected; this is precisely what makes large late-game
battles expensive in the games we are trying to beat on scale. A single global 8 m field — rejected;
25 M cells per field is 50 MB, which does not fit the concurrent-field budget.

---

## R7. Broad-phase spatial index

**Decision**: Uniform grid sized to the longest weapon range (about 128 m, roughly 97,000 cells),
rebuilt every tick by counting sort, units within a cell ordered by arena index.

**Rationale**: Counting sort is linear, allocation-free after warm-up, and produces an ordering
determined entirely by integer cell coordinates and arena indices — deterministic with no sorting
of floats or tie-break rules. Target acquisition and collision then read only neighbouring cells.

**Alternatives considered**: A quadtree or BVH — rejected; rebuild cost and pointer chasing are
worse for uniformly distributed mobile entities, and tree shape would become another ordering
dependency to pin.

---

## R8. Supply network solver

**Decision**: Pressure diffusion over supply links, not a flow algorithm. Each tick, in two passes:
compute every link's transfer from the stock levels at tick start, then apply all transfers. A
link moves `min(capacity, k * (stock_from - stock_to))` in fixed point.

**Rationale**: This satisfies FR-018 exactly and almost for free. Because every transfer is computed
from the same tick-start snapshot, the result cannot depend on link iteration order. Because
transfer is proportional to the difference, the system converges instead of oscillating. It is
`O(links)`, needs no graph algorithms at all, and handles network splits, multiple sources, and
capacity limits with zero special cases.

It also *is* the design metaphor rather than an approximation of it: supply as a gradient that
falls off with distance from sources is the literal behaviour of diffusion, so the single tuning
value of FR-019 is the diffusion rate `k` relative to consumption rate.

**Alternatives considered**: Min-cost max-flow per tick — rejected; expensive, and its optima are
not unique, so small changes cause large reroutes, which is visible to the player as flicker and
violates the stability requirement. Per-consumer pull with priority ordering — rejected; the result
depends on the order consumers are visited, which is the thing FR-018 forbids.

## R9. Glyph rendering

**Decision**: One dynamic mesh containing every visible glyph, rebuilt at simulation rate rather
than frame rate, drawn in a single `Mesh2d` call. Each vertex carries both its previous and its
next position; a uniform interpolation factor lerps between them in the vertex shader.

**Rationale**: This is the choice that makes the unit-count target reachable on the render side. It
avoids 20,000 Bevy entities and their change detection entirely, moves the CPU cost to 10 Hz
instead of 60+ Hz, and satisfies FR-036 by doing the smoothing on the GPU. At roughly eight
vertices per glyph, 20,000 glyphs is 160,000 vertices — a single trivial draw call.

**Alternatives considered**: One Bevy entity with a `Sprite` per unit — rejected; ECS overhead and
per-frame transform propagation at 20,000 entities is real, and it would need texture assets, which
Principle V forbids. Custom instanced rendering with a per-instance buffer — a valid and more
scalable option that Bevy supports, but rejected for now as more machinery than a single dynamic
mesh needs; revisit only if measurement demands it.

## R10. Terrain rendering

**Decision**: Contours by marching squares over the height field, generated once per map into a
static line mesh. Water as a region mask, generated from the same height field, with the hatch
pattern produced procedurally in the fragment shader from world-space coordinates.

**Rationale**: Both are pure functions of the seed, so both satisfy Principle V without argument.
Generating the hatch in the shader rather than as geometry keeps line weight constant on screen
across the full zoom range, which a geometry-based hatch would not.

**Alternatives considered**: A height-shaded raster — rejected; it reads as a terrain map rather
than a staff display, which is the entire visual thesis. Hatch as generated geometry — rejected;
zoom behaviour is wrong and the vertex count is pointless.

---

## R11. Domain separation

**Decision**: Draw order carries the meaning. Subsurface glyphs are drawn *before* the water layer,
so the hatch passes over them; surface and land glyphs after it; air last, offset by a few pixels
with a soft shadow ellipse projected at its ground position, the offset scaling with zoom so it
reads as parallax.

**Rationale**: This satisfies FR-007 with no UI at all — no toggles, no filters, no modes. Occlusion
by the water hatch is a physical metaphor the eye resolves without being taught, and the offset plus
shadow is the standard cartographic cue for altitude. Shape encodes domain redundantly (FR-008), so
the reading survives even where layering is ambiguous.

**Alternatives considered**: Layer toggles in the style of naval warfare simulators — rejected; it
splits attention and turns a perception problem into a UI task. Colour-coding domains — rejected;
colour is already committed to ownership, and the palette is deliberately pale.

## R12. The hostile force

**Decision**: Territory on a coarse sector grid (about 512 m, roughly 6,100 sectors). Held sectors
spread to adjacent unheld ones at a fixed rate; committed force is a function of sectors held;
attacks launch from held sectors toward the nearest player holding.

**Rationale**: This satisfies FR-022 and FR-023 with rules a player can read off the map, and it
never fails to work — there is no reasoning to get wrong. It reuses the sector grid the pathing
layer already needs. Pressure scaling with area held makes retaking territory pay off immediately
and visibly, which is what makes it an opponent rather than a spawner.

**Alternatives considered**: A base-building skirmish opponent — explicitly out of scope; it is the
classic load-bearing wall this project is structured to avoid, and it can be added later through the
same command interface.

---

## R13. Parallelism

**Decision**: The simulation is single-threaded through the first eight increments. Parallelism is
introduced only in the final increment, only after measurement shows the tick budget is actually
threatened, and only in phases with disjoint writes or integer reductions.

**Rationale**: Premature parallelism is the single largest determinism risk in the project, and the
10 ms budget at 20,000 units is plausibly reachable single-threaded for most phases. Deferring it
costs nothing because Principle IV already constrains how it may be added, so no restructuring is
implied.

**Alternatives considered**: Parallel from the start — rejected; it would mean debugging
determinism and concurrency simultaneously, during the period when neither is yet proven.

---

## R14. Increment structure and manual checkpoints

**Decision**: Nine increments, each ending in a build that runs and can be played with, and each
carrying an explicit question for the author to answer by hand before the next begins. Three of them
are marked as decision gates where the answer may change the design rather than merely confirm it.

**Rationale**: Two forces require this. Principle I demands that every layer be independently
deliverable, so an increment that cannot be delivered alone is malformed. And this is a game: whether
the supply model is interesting, whether the display reads without help, and whether fighting blind
is tense rather than annoying are questions that cannot be answered from a document. Discovering the
answer in month five is the failure this structure exists to prevent.

The three gates are deliberately front-loaded relative to their cost. The visual language is proven
in the second increment, not the last, because everything else is built on top of it.

**Consequence for planning granularity**: because the author intends to edit code between
increments, each increment is specified by its contracts and acceptance criteria rather than by the
functions and files it should contain. An increment must depend on what the previous one
*guarantees*, not on what it happened to write, so that hand edits between checkpoints do not
invalidate the plan.

**Alternatives considered**: One pass through all seven user stories — rejected; it violates
Principle I and defers every design question past the point where answering it is cheap. A
checkpoint after every task — rejected as too fine; a checkpoint is only useful where there is
something to feel, and most tasks produce nothing visible on their own.

## R15. Reuse of existing QUIC and RPC crates (deferred)

**Decision**: Nothing from the author's existing `shai` and `cluster` crates enters this slice.
Multiplayer is out of scope here, so no networking code is planned at all. The evaluation is recorded
so the analysis is not repeated when the multiplayer specification is written.

**Rationale**: This slice has no network requirement. Adding a transport dependency now would mean
building infrastructure against requirements that do not yet exist — dedicated servers versus
peer-to-peer, whether there is a lobby service, whether accounts exist — which is the load-bearing
wall pattern Principle I is written to prevent. The extraction cost does not grow by waiting, while
the quality of the decision does.

**What was evaluated, for the future specification**:

`shai` (about 3,400 lines) — a tower-based request/response RPC over QUIC with an `rkyv` wire format,
a router with extractors, a reconnecting channel, an in-process transport for tests, and mTLS.

- Wrong shape for the tick channel. It opens one QUIC stream per message and finishes it, which for a
  ten-hertz order tape across several peers is a stream per message and a 32-byte header over a
  payload of roughly a dozen bytes, sixteen of which are a trace id with no meaning in a match.
- More importantly, a reliable ordered stream is the wrong transport for lockstep at all. One lost
  packet stalls the order tape for a round trip, and every participant sees the stutter. The correct
  technique is redundant transmission over unreliable datagrams — each packet carries the orders for
  the last several ticks, so loss costs nothing and retransmission is never needed. `quinn` supports
  datagrams; `shai` uses only bidirectional streams.
- Right shape for everything around the match: lobby, join, map transfer, chat, recording upload.
  That is genuinely request/response and `shai` fits unchanged.
- Directly reusable regardless of shape: the `rkyv` approach with forced little-endian, which this
  plan already adopts for state and fingerprints (R5); the length-prefixed frame codec pattern; the
  `quinn` plus `rustls` configuration boilerplate; and the in-process transport, which is exactly the
  pattern needed for deterministic network tests.

`cluster` (about 950 lines) — identity and deployment on top of `shai`: a private certificate
authority, mTLS with client certificate verification, worker identity from certificate fingerprints,
DNS resolution with parallel dialling, a tower middleware stack, and OpenTelemetry injection.

- The trust model does not transfer. It authenticates workers the operator issued certificates to;
  a game authenticates strangers. Per-player certificates from a private CA means operating a PKI.
- Its transport tuning is for the opposite traffic. Its own comment says it is optimised for small
  RPC request/response: 256 concurrent bidirectional streams, a 1 MB stream window and a 64 MB
  connection window, with no datagram buffer configured. Its 15-second keepalive and 45-second idle
  timeout are far too slow for noticing a dropped player.
- `dial.rs` is the one piece worth lifting wholesale — DNS resolution with parallel dialling,
  per-family bind addresses, and fallback is fiddly code that a lobby client needs and that is
  annoying to get right.

**Extraction cost, when the time comes**: `shai` needs its `lifetime` dependency removed (backoff
and jitter, trivially reimplemented), carries `shai-macros` along, and uses a nightly feature that
would be dropped by boxing one future. `cluster` needs its `protocol` dependency cut, which means
removing or vendoring the `auth` module, and its OpenTelemetry feature disabled.

**Alternatives considered**: Extracting both into standalone crates now so they are ready later —
rejected above. Adding a minimal networking layer to this slice so the design is proven early —
rejected; the reproducibility requirements already prove everything networking depends on, and
proving them is cheaper without a socket involved.

**Addendum — intended multiplayer topology** (2026-09-16, for the future specification): the author
intends peer-to-peer with a server for lobbies, which is the architecture of the reference game.
Recommendation for the multiplayer specification is to relay the lockstep channel through that same
server rather than connecting peers directly. The hard part of peer-to-peer is NAT traversal, not
lockstep; but lockstep traffic is a few hundred bytes per second per player, so relaying eight
players costs roughly 8 KB/s per match and removes ICE entirely. It also gives the server the
complete order log — which is the recording — and a view of every peer's fingerprint, so desync is
detected centrally and the diverging peer named. Known limitation to carry forward: peer-to-peer
lockstep cannot prevent map hacking, since every peer simulates the whole world. This matters more
here than in a conventional RTS because the intelligence picture is the game.
